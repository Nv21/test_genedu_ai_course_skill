# wikipedia-trend-insights — довідник для захисту проєкту

Цей документ для людини, яка захищає проєкт: що робить навичка, як влаштований код, які функції викликаються і в якому порядку, чому ухвалено саме такі рішення, як перевірено результат і які є обмеження. Інструкції для агента лежать у [`SKILL.md`](../SKILL.md), план розвитку — у [`development-roadmap.md`](development-roadmap.md), деталі API — в [`api-reference.md`](api-reference.md).

---

## 1. Що це і навіщо

**Задача.** B2C-продуктовій команді треба вирішити, на які теми, мови чи ринки орієнтуватися. Навичка перетворює питання звичайною мовою («чи росте інтерес до астрономії в українській Вікіпедії і наскільки цьому можна довіряти?») на результат, що спирається на дані:

1. **Стаття для кожної мови.** Тема знаходиться в кожному мовному розділі, і для кожної відповідності вказано, наскільки вона надійна.
2. **Тренд.** Для кожної мови рахується відсоток зміни, статистична значущість, аномалії та мітка довіри з поясненням.
3. **Графік порівняння** (PNG).
4. **PDF-звіт** на 1–3 сторінки (максимум 5), який можна переслати команді.
5. **JSON з усіма числами.** З нього агент пише відповідь, а не «з голови» і не з картинки.

Окрема команда `rising` відповідає на питання, де тему ніхто не назвав: «які теми зараз найшвидше ростуть у мовному розділі чи країні».

**Джерело даних:** Wikimedia Pageviews REST API (перегляди статей з 2015-07) і Wikidata (зв'язок однієї теми між мовами). Обидва відкриті, ключ не потрібен.

## 4. CLI: команди, параметри, коди виходу

Запускати завжди через `./.venv/bin/python3 scripts/wiki_trends.py <команда>`.

| Команда | Що робить | Функція |
|---|---|---|
| `doctor` | Перевіряє, що залежності імпортуються і API відповідає | `cmd_doctor` |
| `resolve --topic --langs` | Лише знаходить статтю для кожної мови, переглядів не завантажує | `cmd_resolve` → `resolve_topic` |
| `study ...` | Весь ланцюжок: знаходження статей → перегляди → статистика → графік → PDF → JSON | `cmd_study` → `run_study` |
| `rising --targets` | Шукає статті, які найшвидше ростуть рік до року | `cmd_rising` → `discover_rising` |

**Ключові параметри `study`:**
- `--topic` або `--articles "pl:Tytuł,cs:Název"`;
- `--langs`;
- `--start` / `--end`;
- `--granularity monthly|daily`;
- `--metric views|share`;
- `--recommendation` або `--recommendation-file`;
- `--title`, `--out`, `--cache-dir`.

**Ключові параметри `rising`:**
- `--targets uk,pl,en,US` (малі літери — мовний розділ, великі — країна);
- `--end`, `--window 3`, `--top 5`, `--verify 40`, `--out`.

**Коди виходу:**

| Код | Значення |
|---|---|
| 0 | успіх |
| 1 | `doctor`: API недоступне |
| 2 | некоректні параметри (`ValueError`) або не встановлені залежності |
| 3 | `study`: аналіз виконано, але звіт перевищив 5 сторінок, тож PDF не створено (JSON і PNG збережено) |

## 5. Що саме викликається: потік виконання

### 5.1 `study` — повний ланцюжок

```
scripts/wiki_trends.py main()
 └─ cmd_study(args)
     ├─ parse_articles_arg(--articles)               pipeline.py
     └─ run_study(...)                               pipeline.py
         ├─ перевірка параметрів (metric, granularity)
         ├─ parse_boundary(start/end)                dates.py
         ├─ обрізання до DATA_AVAILABLE_SINCE (2015-07-01) + caveat
         ├─ WikimediaClient(cache_dir)               api.py
         ├─ resolve_topic(client, topic, langs)      resolve.py
         │    ├─ ручні назви (--articles) → method=manual, confidence=high
         │    ├─ client.wikidata_search(topic)       → QID, лише при точному збігу label/alias
         │    ├─ client.wikidata_sitelinks(QID)      → назва статті в кожній мові
         │    └─ для мов без sitelink: client.wiki_search(lang, topic)
         │         ├─ збіг слів з темою → search_fallback, confidence=low
         │         └─ немає спільних слів → confidence=none, без вгадування
         ├─ для кожної мови:
         │    ├─ client.pageviews_per_article(...)   api.py (кеш)
         │    ├─ client.pageviews_aggregate(...)     лише для metric=share
         │    └─ analyze_series(points, totals)      stats.py → TrendResult
         ├─ _build_ranking(trends)                   by_growth / by_current_interest / by_confidence
         ├─ caveats для мов з низькою довірою
         ├─ charts.render_comparison_chart(...)      → .png
         ├─ _auto_findings(labels, trends)           текстові спостереження з чисел
         ├─ report.build_pdf(...)                    → .pdf (або ReportTooLongError)
         └─ запис .json
```

### 5.2 Кешування й мережа (`api.py`, `cache.py`)

- **`WikimediaClient._get_json`** робить HTTP GET:
  - 404 означає «немає даних» і не вважається помилкою;
  - на 429 робить до 5 повторів з паузою, яку вказує `Retry-After`, або з експоненційною (5, 10, 20… с);
  - інші помилки піднімають `WikimediaAPIError`.
- **`_cached_call`** обгортає кожен запит у `DiskCache.get_or_fetch` і рахує `requests_made` / `cache_hits`.
- **TTL** (`_cached_ttl_for_range`): якщо діапазон закінчився понад 35 днів тому, дані вже не змінюються і кешуються назавжди. Свіжі дані кешуються на 6 годин, бо поточний місяць ще «доростає».
- **`DiskCache`**: один JSON-файл на ключ, ім'я — sha256 від ключа. Індекс не потрібен, і паралельні процеси не псують записи одне одного.
- **Методи клієнта:**
  - `pageviews_per_article` — перегляди однієї статті;
  - `pageviews_aggregate` — усі перегляди розділу, для `share`;
  - `wikidata_search`, `wikidata_sitelinks`, `wiki_search` — пошук статті;
  - `top_articles_month`, `top_articles_country_day`, `site_info` — для `rising`.

### 5.3 `rising` — пошук тем, що ростуть

```
cmd_rising(args)
 └─ для кожного target: discover_rising(client, target, end_month, window, top_n, verify_k)
     ├─ recent = останні `window` повних місяців; base = ті самі місяці рік тому
     ├─ _month_top(target, month) для recent і base
     │    ├─ мова: client.top_articles_month(project, y, m)          топ-1000 за місяць
     │    └─ країна: client.top_articles_country_day(C, дні 1/8/15/22) → оцінка місяця
     ├─ кандидати = статті, що є в топі КОЖНОГО з recent-місяців
     ├─ фільтри: _is_content (головна сторінка, службові простори назв з site_info),
     │           _JUNK_RE (.php/.phtml), _YEAR_RE (рік у назві → щорічні події)
     ├─ попередній рейтинг: recent_avg / base (відсутня в base → «поріг» списку = нижня межа росту)
     ├─ перевірка top verify_k: pageviews_per_article за 24 міс. → точний YoY + analyze_series
     └─ розподіл: rising (стабільний ріст) / news_spikes (spike_sensitive) / new_topics (рік тому < 500 переглядів/міс.)
```

### 5.4 PDF (`report.py`)

- **`build_pdf(...)`** створює `_Doc`, викликає `_layout` і рахує сторінки:
  - понад 5 сторінок — `ReportTooLongError`, файл не пишеться;
  - 4–5 сторінок — попередження;
  - далі `PdfPages` записує всі сторінки з номерами «стор. X / N».
- **`_Doc`** — «курсор» у дюймах, що рухається вниз сторінкою. `ensure(h)` починає нову сторінку, якщо блок висотою `h` не вміщається.
- **Порядок блоків у `_layout`:** заголовок → графік → таблиця (`_draw_table`, при переносі повторює заголовок) → спостереження → блок висновку (`_draw_recommendation`, при переносі — «(продовження)») → обмеження → колонтитул.

## 6. Статистика: як рахується і чому саме так (`stats.py`)

**`analyze_series(points, totals, metric)` → `TrendResult`:**

1. **Метрика:**
   - `views` — сирі перегляди.
   - `share` = перегляди статті / усі перегляди розділу × 1 000 000, тобто «переглядів на мільйон». Без цього велика англійська Вікіпедія завжди «перемагала» б малу чеську.
2. **Ріст, %** = середнє **останніх 3** точок / середнє **перших 3** − 1. Беремо по 3 точки, а не першу й останню, щоб один шумний місяць не визначав результат.
3. **Лінійна регресія** (`scipy.stats.linregress`) дає нахил, R² і p-value нахилу.
4. **Аномалії.** Для залишків від лінії тренду рахується робастний modified z-score (медіана/MAD, Iglewicz & Hoaglin); |z| > 3.5 — аномалія. Відхилення міряються від тренду, а не від ковзного вікна, бо ковзне вікно пропускає сплеск на краю ряду (саме тоді, коли тема «щойно вибухнула»).
5. **Залежність від сплеску (`spike_sensitive`).** Регресія перераховується без аномалій. Якщо знак нахилу змінився або нахил зменшився більш ніж удвічі, тренд тримається на сплеску.
6. **Мітка довіри (`_confidence_label`)**, правила застосовуються згори донизу:

| Умова | Довіра |
|---|---|
| точок < 6 | low |
| немає варіації | low |
| `spike_sensitive` | low («разовий вплив») |
| p < 0.05 **і** R² ≥ 0.3 | high |
| p < 0.1 | medium |
| інакше | low («шум переважає») |

**Чому поєднуємо p-value і R².** p-value відповідає на питання «чи тренд не випадковий», а R² — «наскільки ряд прямий». Значущий, але дуже шумний ряд отримує medium, а не high. Сезонність цю оцінку більше не псує: див. STL нижче.

### 6.1 Розклад на тренд і сезонність (STL)

- **Бібліотека:** `statsmodels.tsa.seasonal.STL` (robust, період 12). Запускається для місячних рядів від 24 точок (два повних цикли).
- **Мультиплікативно, через логарифм.** Сезонність переглядів пропорційна рівню: «вересень утричі вищий» і при 10 тис., і при 1 тис. переглядів. Адитивний STL на ряді, що впав на 90%, бачив би спадні вересневі піки як шум. Для астрономії сила сезонності в адитивному варіанті була 0.24, у логарифмічному — 0.75.
- **Що дає:**
  - `trend_change_pct` — зміна згладженого тренду за весь період;
  - `trend_change_12m_pct` — зміна тренду за останні 12 місяців;
  - `seasonal_strength` — F_S за Hyndman (FPP3 §4.3), від 0 до 1;
  - `seasonal_amplitude` — у скільки разів типовий піковий місяць вищий за найнижчий;
  - `seasonal_peak_month` — місяць піку;
  - пунктирна лінія тренду на графіку.
- **Коли сезонність «важлива»:** F_S ≥ 0.4, амплітуда ≥ 20% **і пік повторюється**: піковий місяць щонайменше у двох роках ≥ ×1.1 від медіани свого року, причому найсильніший такий рік не більш ніж учетверо сильніший за найслабший (v1.1). Третя умова з'явилася після baseline: на 24 місяцях STL давав F_S = 1.0 від одного сплеску (Oliver Tree), і сплеск зникав з детекції. Лише тоді регресія, аномалії й довіра рахуються на ряді без сезонності (`deseasonalized: true`). Другий поріг потрібен, бо ідеально регулярне коливання ±4% має високе F_S, але практичного значення не має (це показав тест).
- **Порядок, яке число наводити:** тренд STL → рік до року → «перші 3 проти останніх 3». STL використовує **всі** місяці, а рік до року — лише три. Для астрономії рік до року давав −7.5%, бо порівнював тільки літо, коли інтерес і так мінімальний. STL показав −59% за 12 місяців (вересень: 4 687 → 1 642).
- **Перевірка на синтетиці з відомою відповіддю:** тренд подвоюється за 36 місяців, поверх нього щовересня пік ×2.5. STL відновив +108% (очікувалось ≈ +100%), R² після вилучення сезонності — 0.97.

### 6.2 Режим трьох періодів (`horizons.py`)

Вмикається, якщо користувач не вказав дат, тобто без `--start` і `--end`.

| Період | Дані | Сезонність |
|---|---|---|
| `3m_weekly` | 13 повних тижнів пн–нд; денні дані, підсумовані по тижнях (менше шуму, немає ефекту днів тижня) | кожен тиждень ділиться на коефіцієнт свого місяця з 3-річного розкладу (місяць визначається за четвергом тижня) |
| `1y` | останні 12 повних місяців — зріз 3-річного ряду, **без нового запиту до API** | коефіцієнти з 3-річного розкладу |
| `3y` | останні 36 повних місяців | тут і виконується STL |

- **Зміна за періодом:** для 3 років і 1 року — тренд STL; для 3 місяців — перші 3 тижні проти останніх 3 (після вилучення сезонності).
- **Напрям:** `up` / `down` / `flat` (|зміна| < 5%) / `unclear` (довіра low).
- **Підсумок у коді.** `horizon_summary` зводить напрями в один шаблон: `steady_decline`, `decline_flattening`, `reversal_up`, `growth_stalling`, `mixed`… Дешевій моделі не треба зводити три таблиці самій.
- **Чому тижнева картина теж чиститься від сезонності.** Без цього астрономія за останні 3 місяці показувала «+410%», хоча це просто вересень. Після очищення виходить +94% з **низькою** довірою, тобто «без надійного сигналу».
- **Вартість:** один додатковий денний запит на мову.

**Ранжування (`_build_ranking`)** — три незалежні рейтинги й детермінований порядок:
- `by_growth` — за відсотком росту;
- `by_current_interest` — за середнім рівнем;
- `by_confidence` — за довірою;
- `explore_next` — тег за напрямом тренду, до якого належить довіра, а всередині тегу — сортування за рівнем. Тег `turning` означає, що зміна тренду за останні 12 місяців суперечить загальному тренду на ≥5%.

## 7. Як навичка захищає висновки від помилок

- **Знаходження статті.** Wikidata використовується лише при *точному* збігу label або alias. Під час тестів «English language» знаходило Q1860 саме через alias. Пошук по тексту статті дає лише `low`, а якщо в назві немає спільних слів з темою — `none`, і назва не вгадується. Реальний приклад: «intermittent fasting» у pl → статті немає, замість неправдивого «Stres oksydacyjny».
- **Вільний текст лише в одному місці.** Висновок агента (`--recommendation`) — єдиний довільний текст у звіті. Він стоїть у виділеному блоці одразу під таблицею, з якою його можна звірити. Все інше генерується з чисел.
- **`caveats`** автоматично містять:
  - обрізання дат до 2015-07;
  - статті, знайдені пошуком, а не через Wikidata;
  - мови без даних;
  - мови з низькою довірою;
  - перевищення ліміту сторінок.
- **`confidence_reason`** — готове речення, щоб дешева модель не вигадувала пояснень.
- **Правила в `SKILL.md`:** не наводити відсоток росту без довіри; при `none` не продовжувати мовчки; при `low` наводити число, але прямо казати, що це не надійний сигнал.

## 8. Відомі обмеження (краще назвати їх самому)

1. **Мова ≠ країна.** Іспанською читають Іспанія та Латинська Америка; частина українців читає en/ru. Для США є лише дані за країною (`rising`) з вибіркою за днями.
2. **Стаття — це не попит на продукт.** Інтерес до статті «Англійська мова» ≠ бажання вчити англійську. План — кластери тем (roadmap §3).
3. **Сезонність:** STL потребує ≥ 24 місяців. Для коротших рядів лишається лише грубе виявлення піків і рік до року. Тижнева картина чиститься місячними коефіцієнтами, а це наближення. Коли саме тренд змінив напрям, навичка ще не визначає (у roadmap — тест точок зламу).
4. **Боти.** Фільтр Wikimedia `agent=user` пропускає частину автоматичного трафіку (дивні статті в топах).
5. **Кеш** прив'язаний до точного діапазону дат: розширений період завантажується заново.
6. **Шрифти.** Японські й корейські назви статей на графіку відображаються квадратиками; заголовок графіка трохи накладається на службовий напис.
7. **Rate limit.** Паралельні запуски отримують 429. Клієнт повторює запит, але великий `rising` може тривати кілька хвилин.
8. ~~Формулювання для medium~~ виправлено (§9.2).

## 9. Перевірка на дешевій моделі (Claude Haiku 4.5)

**Що вимагає завдання.** Агент, який *керує* навичкою, має бути дешевою моделлю. Він сам читає `SKILL.md`, вирішує, які команди запускати, і пише відповідь користувачу. Перевірити потрібно повний сценарій саме на такій моделі.

**Як перевіряли.** Три незалежні агенти на Claude Haiku 4.5 (субагенти Claude Code з `model: haiku`) отримали лише шлях до навички і запит користувача, без підказок, що вважається правильним. Три запити — приклади із завдання:

1. Інтервальне голодування, pl проти cs, за 2 роки.
2. Астрономія в uk: чи росте і наскільки довіряти.
3. Інтерес до англійської в uk, pl, tr, vi, es, pt: які аудиторії досліджувати далі.

**Критерії оцінки:**
- використано скрипти навички, а не власний код;
- правильні параметри (`share` для порівняння мов, `views` для однієї мови);
- кожен відсоток росту подано разом із довірою;
- `caveats` перенесено у відповідь;
- при `confidence: none` (pl) нічого не вгадано;
- рекомендація спирається на рейтинг і довіру.

**Результати:** див. §9.1 (заповнюється після прогону).

## 10. Як використовувались AI-інструменти і як перевірявся їхній результат

Навичку розроблено з Claude Code. Результат AI не приймався на віру, а перевірявся так:

- **Офлайн-тести** (`python3 -m unittest discover -s tests`, 49 тестів) для статистики, знаходження статей (з фейковим клієнтом), кешу й дат. Частина — регресійні тести на реальні баги, знайдені на живому API (alias у Wikidata, хибний збіг пошуку, сплеск на краю ряду).
- **Живі прогони з ручною звіркою.** Числа в JSON звірялися з помісячними рядами. Наприклад, у в'єтнамській «−32%» перевірили помісячно і побачили, що це здебільшого сезонність, а не спад. Турецький «+132%» перевірили денними даними: це ступінчастий перехід із 30.07, а не сплеск ботів за один день.
- **Візуальна перевірка PDF.** Сторінки рендерились і переглядались; так знайдено переповнення сторінки й вихід тексту за клітинку таблиці.
- **Навмисні крайні випадки:** 6 і 12 мов, задовгий висновок на 4, 7 і 9 сторінок — перевірено попередження й код виходу 3.
- **Перевірка на Haiku** (§9): чи достатньо інструкцій для слабшої моделі.
- **Чесні відмови:** коли даних немає (pl, голодування), навичка це повідомляє, а не заповнює пропуск.

## 11. Типові питання на захисті — короткі відповіді

- **Чи використовуєте бібліотеки для трендів?** Лише прозорі й перевірені: `scipy.stats.linregress` (нахил, p, R²) і `statsmodels` STL (розклад на тренд і сезонність). Prophet чи нейромережі не використовуються: 24–36 точок замало для складних моделей, а кожне число має пояснюватися однією формулою.
- **Чому Вікіпедія?** Це відкриті, безкоштовні дані з 2015 року по 300+ мовах, доступні без ключа, і в них одна тема однаково зв'язана між мовами через Wikidata. Мінус — це лише один показник уваги, тому є план додати інші джерела (roadmap §5).
- **Чому не дати агенту писати код самому?** Разовий код від дешевої моделі не врахує крайніх випадків: alias у Wikidata, хибні збіги пошуку, 404 = немає даних, сплески на краю ряду, нормалізацію `share`, розбиття PDF на сторінки. Одна перевірена команда відтворювана і тестується.
- **Звідки «довіра»?** Правила в §6: p-value + R² + перевірка на сплеск + мінімум 6 точок. Пояснення генерується разом з міткою.
- **Як уникаєте хибних статей?** Wikidata лише при точному збігу; пошук дає не вище `low`; без спільних слів — `none` і список кандидатів.
- **Як працюють повторні запити?** Дисковий кеш: історичні дані назавжди, свіжі — 6 годин; лічильник `api_calls`. У цій сесії перезбірка звітів коштувала 0 запитів до API.
- **Що буде з 30 мовами?** PDF розбивається на сторінки, а після 5 сторінок з'являється вимога розбити дослідження. Далі в плані зведення «топ-N + додаток» і паралельне завантаження з лімітером (roadmap §6–7).
- **Як масштабувати на тисячі статей?** Дампи переглядів Wikimedia замість REST API, кеш у SQLite/DuckDB, злиття діапазонів у кеші (roadmap §6).
